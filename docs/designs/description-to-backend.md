# Design: Project description in, full verified backend out

## Problem Statement

Today the factory needs a hand-written OpenAPI 3.x spec and produces a single-resource CRUD backend on
SQLite with no auth. The goal is for a team member to hand it plain documents (a project description
and design docs) and get a **full working backend**: several related resources, user auth with
per-user ownership, Postgres with migrations, and Docker deployment. The factory's core promise has
to survive this: verification the model cannot fake.

Once the spec is generated, a new gap opens. The checks prove the code matches the spec, but nothing
proves the spec matches what the author meant. A misread description would produce a perfectly
verified wrong backend. The design has to close that gap.

## Demand Evidence

Weak, stated plainly. A teammate or manager has seen a demo on the sample `orders` specs. The
reaction was positive, with no follow-up request, time or budget since. No one besides the author
has run a build. The design is the author's bet on where the factory has to go, not a response to a
request.

## Status Quo

The team writes OpenAPI specs first, then implements them by hand. Specs and code drift apart
(renamed fields, changed status codes, dropped parameters). Nobody measures the time this costs.

## Target User & Narrowest Wedge

- **User:** the team's backend engineers who hand-code services from specs. No individual named yet.
  The Assignment fixes that.
- **Wedge:** a hand-written entities file goes in, and a full backend that passes every check comes
  out. This works before any LLM writes specs (see Phasing), so the most valuable and most
  verifiable part ships first.

## Constraints

- `AGENTS.md` hard rules stay, except rule 2, which is amended (see Premises).
- Python only, including generated code and tooling. `uv`, `mypy --strict`, unit tests for harness
  code.
- Docker becomes a requirement for running the factory, because checks run on Postgres.
- The existing OpenAPI front door (`factory build specs/orders.yaml`) must keep passing. No
  regression for teams that already have specs.

## Premises

Agreed during the session:

1. **Input is prose.** A new LLM station, `spec_writer`, drafts the spec. The run **pauses** until
   the user approves it. `AGENTS.md` rule 2 is amended to: "the LLM may draft the spec, only behind
   schema validation and human approval".
2. **The approved spec is the contract.** Everything after approval is checked against it, as today.
3. **"Full" means four things:** related resources, user auth with per-user ownership, Postgres
   with Alembic, and Docker deploy.
   - Generated from templates, no LLM: the auth plumbing, database config, migrations and
     deployment files.
   - Written by the LLM: only business rules and custom actions.
4. **Checks run against Postgres in Docker, not SQLite,** so tests behave like production.
5. **The gates must grow:**
   - nested resources (today `factory/harness/test_quality.py:100` groups resources by the first
     path segment, so `/projects/{id}/tasks` is grouped under `projects`);
   - required cross-user isolation tests;
   - auth tokens for Schemathesis and for the cheat probe;
   - budgets that scale with the number of operations (today a run gets 8 iterations, 400 lines per
     iteration and $5 in total, from `factory/config.py`).
6. **v1 is proven on one realistic sample description** (users → projects → tasks) before it's
   pointed at anything from work.

## Approaches Considered

- **A: Front door first.** Add spec_writer to today's pipeline, then add features one at a time.
  Rejected: auth and ownership added later would force rework of templates and gates.
- **B: Full stack, OpenAPI in the middle.** The LLM drafts full OpenAPI for approval. Rejected: a
  500+ line spec gets skimmed rather than reviewed, and the model would infer ownership from prose.
- **Superseded by the reframe:** a timed real-spec demo, drift detection on an existing service,
  and real-spec readiness. These were aimed at proving today's factory. The user redirected the
  session to building from descriptions.

## Recommended Approach: Entity model in the middle (C)

### The entities file

`spec_writer` reads the description and design docs and writes a short, typed `entities.yaml`. The
user reads and approves that file instead of OpenAPI. Example for the sample project:

```yaml
app: tasks
auth: jwt                    # generates users, /auth/signup, /auth/login, current-user dependency
entities:
  Project:
    owner: user              # rows belong to the creating user; other users get 404
    fields:
      name: {type: str, min: 1, max: 200}
      archived: {type: bool, default: false}
    rules:
      - "An archived project rejects new tasks with 409."
    actions:
      archive: {method: POST, returns: Project}   # custom endpoint, body written by the LLM
  Task:
    parent: Project          # nested under /projects/{project_id}/tasks, cascade delete
    fields:
      title: {type: str, min: 1, max: 200}
      status: {type: enum, values: [todo, doing, done], default: todo}
      due: {type: date, optional: true}
    rules:
      - "status only moves todo -> doing -> done; any other transition is 422."
gaps: []                     # spec_writer lists what the description asks for that the format can't express
```

The format is a Pydantic model in `factory/`, so validation needs no LLM. `spec_writer` is never
allowed to invent anything to fill a gap. Anything it can't express goes in `gaps:`, and the user
decides what to do with it.

### Pipeline v2

| # | Station | How | Output |
|---|---|---|---|
| 0 | `draft` | LLM `spec_writer` + Pydantic validation | `entities.yaml`; run pauses |
| – | `approve` | `factory approve <run_id>` | entities hash recorded in `run.json` |
| 1 | `expand` | deterministic (new) | `openapi.yaml` (CRUD, nested routes, `securitySchemes`, examples, `links`), generated auth, ownership and CRUD tests |
| 2 | `lint` | existing | catches expansion bugs, because the generated spec must pass the same rules |
| 3 | `scaffold` v2 | Jinja2 | Postgres config, Alembic migration, auth module, ownership dependency, Dockerfile, compose file |
| – | `setup` | `uv sync` + Postgres container per run | a fresh database per check run |
| 4 | `test_writer` | LLM, existing gates | behaviour tests for `rules:` and `actions:` only |
| 5 | `coder` | existing loop | business rules and action bodies |
| 6 | `contract` | Schemathesis + auth hook | contract result on a fresh Postgres database |
| 7 | `sdk` | existing | client |
| 8 | `deploy_check` | new | `docker compose up`, then `/health` and one authenticated round trip |
| 9 | report | existing + entities and approval | `report.md` and `run.json` |

**Invariant:** the coder cannot change the database schema. Tables, columns and migrations come only
from the approved `entities.yaml`. If a business rule needs a new column, that's an entities change,
and it goes back for approval. This keeps the database design under human approval and outside what
the model controls.

### Verification additions

- **Generated, read-only tests** for each owned entity:
  - user B gets 404 on user A's rows;
  - unauthenticated requests get 401;
  - create, then read back through the nested route.

  These sit alongside the test writer's suite, and neither agent can edit them.
- **Static gate:** resources are grouped by entity from `entities.yaml`, not by path segment.
- **Cheat probe:** the hardcoded implementation also has to fail the ownership tests.
- **Schemathesis:** the harness signs up a user and passes the token. Stateful phases follow the
  generated `links`.
- **Budgets:** iterations, cost and changed-line limits scale with the operation count. The formula
  lives in `factory/config.py`.

### Phasing (deterministic first, LLM spec-writing last)

1. **Phase 7: entities format and expander.** Pydantic schema, `expand` to OpenAPI and generated
   tests, unit tests. The sample `examples/tasks/entities.yaml` is written by hand.
2. **Phase 8: project template v2.** Postgres, Alembic, auth, Dockerfile and compose file. Checks
   run on Postgres in Docker.
3. **Phase 9: gates v2.** Entity-based grouping, ownership tests in the cheat probe, Schemathesis
   auth, scaled budgets.
4. **Phase 10: spec_writer.** `factory draft`, `factory approve`, prompt templates under
   `factory/templates/prompts/`, a scripted scenario so the e2e tests run without an API key.
5. **Phase 11: deploy_check and report updates.**

After Phase 9, a hand-written `entities.yaml` already produces a full verified backend. That's
demoable with no LLM writing specs. Phase 10 adds the prose front door on top of a core that's
already proven.

## Open Questions

1. **Format coverage.** v1 has no many-to-many relations, unique constraints across fields,
   computed fields (the orders `total`), or roles beyond owner. Which of these do the team's real
   services need?
2. **Spec changes over time.** When `entities.yaml` changes, can Alembic autogenerate produce the
   migration deterministically and safely? How does `incremental.py` handle an entity rename versus
   a drop and re-add?
3. **Postgres speed.** One container per run with `CREATE DATABASE ... TEMPLATE` per check is the
   plan. Measure whether 8+ check runs stay within acceptable time.
4. **Schemathesis and auth.** Negative-phase tests may hit 401 before reaching validation logic.
   That needs tuning so contract coverage doesn't silently drop.
5. **The OpenAPI front door.** Should hand-written OpenAPI specs also get v2 features (auth,
   Postgres), or stay v1-only?

## Success Criteria

- `factory draft examples/tasks/description.md` produces a valid `entities.yaml` of 80 lines or
  fewer, with an empty or accurate `gaps:` list.
- After `factory approve`, `factory build` ends `passed`, which requires all of these:
  - all gates pass;
  - zero Schemathesis failures with auth, on Postgres;
  - the generated cross-user tests pass;
  - `deploy_check` is healthy.
- A scripted cheat scenario on `tasks` fails the run, the same way `orders_cheat` does today.
- `specs/orders.yaml` and `orders_v2.yaml` still pass. No regression.
- **The real test:** a backend engineer who isn't the author writes a description, approves the
  entities file, and gets a passing build without editing anything else.

## Distribution Plan

Internal tool. Engineers install it from the repo with `uv tool install`, which requires Docker. CI
(GitHub Actions running the scripted e2e scenarios) stays on the roadmap, after Phase 11.

## Dependencies

- Generated project: Alembic, a JWT library and a password hasher (picked in Phase 8).
- `AGENTS.md`: rule 2 amendment; README pipeline and roadmap updates.
